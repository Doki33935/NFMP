# Аудит NFMP от 10.08.2026

## Итог

Критические блокеры предыдущего аудита устранены. Код и контейнерная конфигурация готовы к контролируемому production-запуску после настройки домена, уникальных секретов и пароля администратора на целевом сервере. Проект имеет серверную ролевую модель, строгую валидацию, хешированные пароли, HttpOnly-сессии, автоматические тесты, CI и отдельную production-конфигурацию.

## Исправлено

- Удалены встроенные реквизиты `111/111` из кода и документации. Первый администратор создаётся только из переменных окружения.
- Все сохранённые plaintext-пароли автоматически переведены в bcrypt; новые пароли содержат не менее 12 символов и требуют подтверждения.
- JWT перенесён в `HttpOnly`, `Secure` в production, `SameSite=Strict` cookie; срок сессии сокращён до 8 часов.
- Добавлено ограничение попыток входа: 5 ошибок за 10 минут для пары IP/логин.
- Права на создание, чтение, взятие, изменение, завершение и скрытие пожара проверяются сервером.
- Взятие пожара выполняется атомарным условным `UPDATE`; чужую карточку дознаватель изменить не может.
- Исправлена ошибка SQLAlchemy `Query.get()` после commit, приводившая к HTTP 500 при успешной записи.
- Добавлена валидация площади, строк, дат, координат Оренбургской области, справочников и связи сельсовета с МО.
- Статусы, роли, координаты, площадь и номер внешней карточки защищены ограничениями PostgreSQL.
- Desktop DTO синхронизированы с API (`creator/reviewer`, `participant_events`, `time_msg`); открытый пожар берётся через `/take`.
- Пожары удаляются только мягко. Из 10 000 нагрузочных записей 9 000 скрыты, 1 000 оставлены для демонстрации.
- Пользователи отключаются мягко и могут быть восстановлены без потери истории карточек.
- Автобекап выполняется раз в 24 часа, проверяется через `pg_restore --list`, хранится 7 дней и не более 7 файлов.
- Удалённое восстановление БД отключено по умолчанию и доступно только при явном `ENABLE_REMOTE_RESTORE=true`.
- Добавлены production Compose, Nginx, Caddy/TLS, внутренние сети, healthchecks и отключение Swagger в production.
- Исправлены ESLint-ошибки, зависимости закреплены по версиям, npm/pip audit не находят известных уязвимостей.
- Добавлены pytest-интеграционные тесты и GitHub Actions для backend, frontend и Compose.
- Страницы фронтенда разделены на ленивые чанки; мобильная шапка не создаёт горизонтального переполнения.
- Экспорт мониторинга формирует настоящий UTF-8 CSV вместо HTML-файла с ложным расширением `.xls` и защищён от spreadsheet formula injection.

## Остаточные риски перед публикацией

- Демонстрационный пароль администратора в существующей локальной БД нельзя переносить на публичный сервер. Для чистой БД задайте уникальный `INITIAL_ADMIN_PASSWORD`; при переносе dump смените пароль через профиль до открытия внешнего доступа.
- Автоматические dump-файлы находятся на том же сервере. Для защиты от отказа диска настройте внешнюю зашифрованную копию каталога `backups/`.
- Тайлы OpenStreetMap и поиск Nominatim требуют интернета. Уже загруженный интерфейс позволяет поставить координату без поиска адреса, но подложка карты без сети недоступна.
- Ограничитель попыток входа хранится в памяти каждого backend-worker и сбрасывается при рестарте. Для публичного высоконагруженного контура следующий уровень защиты — rate limit в Caddy/Redis.
- Тесты показывают предупреждения о будущей несовместимости Starlette TestClient/httpx и удалении `crypt` в Python 3.13. Текущий Python 3.12 не затронут; зависимости следует обновить до перехода на Python 3.13.
- Backend-образ пока запускается от `root` и содержит build toolchain. Для следующего этапа hardening следует перейти на multi-stage сборку и непривилегированного пользователя контейнера.
- CI покрывает API, lint, production build, dependency audit и Compose, но не браузерный E2E-сценарий. Вход, меню, мониторинг 1001 записи, кластеризация карты и отсутствие console errors проверены вручную.

## Эксплуатационные рекомендации

- Хранить копии `backups/` также на отдельном зашифрованном носителе или в объектном хранилище.
- Перед первым production-запуском задать уникальные `POSTGRES_PASSWORD`, `SECRET_KEY`, `INITIAL_ADMIN_PASSWORD`, домен и `CORS_ORIGINS`.
- Проводить плановую проверку восстановления на отдельной БД минимум раз в месяц.
- Следующим этапом добавить журнал действий (`кто/когда/что изменил`).
